# Веб-приложение для премий фракций — разбор и план

Статус: разбор закончен, решения приняты (раздел 6). Решения из разделов 6–10 имеют приоритет над ранними набросками в разделе 4. Следующий шаг — кликабельный прототип (раздел 10, этап 1).

## 1. Две модели расчёта

| | LSPD (WPS, последняя) | SASPA (Google + скрипт) |
|---|---|---|
| Основа | **Баллы за действия**: 27 действий × тариф | **Бюджет и доли**: недельный бюджет → офис → отделы по весам → сотрудники по «% вклада» |
| Формула | MIN(баллы × 500 × множитель должности, 250 000) | Офис: фиксированная ставка по рангу (13 → 250 000, 12 → 200 000). Отдел: FLOOR(бюджет отдела × %, 1000) |
| Выплата | Наличные или электронно (комиссия 2,91%), статус, дата, примечание | Статус «✅ Выдано / ❌ Не выдано» |
| Закрытие недели | 6 ручных шагов с копированием | Меню «Сформировать итог»: архив + отдельная публичная Google-таблица («витрина») |
| Отделы | Офис шефа, PB, CIS, PAI, SWAT, IAD | Офис, HRD, EMD, IAD, ERD, FPW, FPSD |

Вывод: в приложении модель расчёта задаётся настройкой организации. Реестр, недели, ведомость, архив, статистика и журнал правок для обеих моделей общие.

## 2. Что умеет скрипт (меню «🏆 Премии»): это нужно перенести
- **Новая неделя**:
  - спрашивает дату понедельника и проверяет, что веса = 100% и сумма бюджетов = остатку;
  - пересоздаёт лист «Неделя» из тех, у кого «В премии = ДА».
- **Сформировать итог**:
  - проверяет данные: нет % вклада, нулевая премия, нет паспорта;
  - исправляет округление: остаток бюджета отдела отдаёт тому, у кого наибольший %;
  - строит «Итог» со статусами;
  - создаёт публичную витрину-таблицу в Drive («Премии/Витрина»);
  - пишет сводку в `__archive__`, а премии по людям в `__emp_archive__`.
- **Добить до бюджета**: раскидывает остаток бюджета **случайно** по 1 000 между сотрудниками с премией > 0.
- **История недель, Статистика** (4 недели / 8 недель / 3 месяца / всё время):
  - тренд, максимум и минимум;
  - топ-5 (без офиса);
  - разбивка по отделам.
- **Карточка сотрудника**: недель с премией, всего получено, средняя, максимум, история выплат.
- **Управление сотрудниками**:
  - сайдбар добавления и удаления;
  - сортировка по группам рангов (Офис 13–12 → Начальники 11 → Замы 10 → Состав 9–3) и по отделам;
  - цвета отделов.
- **Остальные пункты меню**: «Очистить состав», «Снять всех с премии», «Конфигурация» (бюджет, отделы, веса, имя начальника для подписи в PDF; сам PDF не сделан).
- **onEdit**:
  - журнал правок (ранг, ставка, «в премии», веса) в `__log__`;
  - веса работают в обе стороны (меняешь сумму → пересчитывается %);
  - индикатор «сумма % по отделу = 100%»;
  - счётчик «выдано X из Y».

## 3. Проблемы, которые приложение должно убрать
1. **Сотрудник опознаётся по имени.** Переименование рвёт историю, однофамильцы смешиваются (премии ищутся по имени, удаление тоже по имени). Нужен постоянный ID.
2. **Листы связаны живыми формулами.** «Итог» за 11.05 ссылается на «Неделю», которая уже пересоздана под 22.06. Поэтому в образце «Выплачено 2 526 000 / Начислено 500 000 / Остаток −2 026 000». Закрытая неделя должна быть неизменяемым снимком.
3. **«Новая неделя» удаляет старый лист без возможности вернуть.** Если итог не сформирован, введённые % пропадают.
4. **Статус выдачи не архивируется:** в `__emp_archive__` только премия. История «кто получил, а кто нет» теряется.
5. **История в карточке сортируется по строке «дд.мм.гггг»** (сравнение `localeCompare`). Порядок ломается на стыке месяцев и лет.
6. **Периоды статистики считаются по количеству строк архива** («3 месяца» = последние 12 записей), а не по датам.
7. **«Добить до бюджета» случайный:** результат не повторить и не объяснить. Лучше пропорционально вкладу, с предпросмотром.
8. **Журнал правок неполный:**
   - имя пользователя часто приходит как `unknown` (ограничение onEdit);
   - правки % вклада и статусов не пишутся.
9. **Apps Script медленный:** пересборка листов, `sleep`, лимиты Google.
10. **Ошибки из WPS:**
    - в «В архив» отдел записан кириллицей «РВ», а везде латиницей «PB»;
    - в инструкции B4 вместо C4;
    - в «К выплате» F80 висит лишняя формула `=MIN(1.2)`;
    - пробелы в конце имён и паспортов;
    - ровно 10 строк на отдел.

## 4. Приложение

**Модель данных (черновик):**
- `Organization`: название, модель расчёта (`points` | `budget`), настройки.
- `Department`: название, цвет, порядок, признак «фиксированные ставки» (Офис).
- `Employee` (ID): имя, паспорт, отдел, должность, ранг, ставка, «в премии», история переводов.
- `Week`: дата начала, статус (`open` → `review` → `closed`), **снимок настроек** (тарифы, множители, бюджет, веса).
- `Entry` (неделя × сотрудник): количество действий или % вклада; начислено, способ, комиссия, к выдаче, статус, дата выдачи, примечание.
- `AuditLog`: кто, когда, что, было → стало. Пишутся все правки.

**Экраны:**
1. **Неделя (ввод):**
   - группы по отделам, переход по ячейкам с клавиатуры, +/−, поиск;
   - расчёт и проверки сразу: 100% по отделу, недельный максимум, пустой паспорт;
   - строк сколько угодно.
2. **Ведомость:** выдача одним кликом (дата ставится сама), фильтр «не выдано», прогресс, итоги по способам выплаты.
3. **Закрыть неделю** одной кнопкой: проверки → снимок → новая неделя с тем же составом. Неделю можно открыть заново с записью в журнал.
4. **Сотрудники:** реестр, карточка с историей и графиком, переводы, массовые действия («снять всех с премии»).
5. **Статистика:** периоды по датам, топы, отделы, тренды, графики.
6. **Настройки:** тарифы и множители (LSPD), бюджет и веса в обе стороны (SASPA), отделы, ранги, ставки.
7. **Публичная ссылка на итог недели**, только для чтения. Заменяет витрины-таблицы в Drive.
8. **Журнал правок.**

**Экспорт в WPS Cloud:**
- **Основной вариант:** кнопка «Скачать .xlsx» (ExcelJS) в нынешнем оформлении, с живыми формулами и выпадающими списками. Файл загружается в WPS Cloud и там остаётся полноценной таблицей. Можно выгружать текущую неделю, ведомость или весь архив.
- **Автоматическая синхронизация:** у eu.wps.com публичного API для загрузки файлов я не нашёл (есть только китайский open.wps.cn). Нужно проверить AirScript на вашем аккаунте: таблица сама забирает данные из приложения по ссылке.
- Кнопка «Копировать таблицу», чтобы вставить её в WPS через Ctrl+V.
- Импорт из WPS (.xlsx), чтобы перенести текущих сотрудников и неделю.

## 6. Решения (24.11.2026)
1. **Самостоятельный универсальный продукт.** Любая фракция или организация сама настраивает отделы, должности, действия и правила расчёта. LSPD и SASPA — просто два готовых шаблона.
2. **Вся работа идёт в приложении.** Файл WPS — только итоговый отчёт для проверки админами. Отсюда:
   - обратная синхронизация с WPS не нужна;
   - нужен аккуратный, читаемый и проверяемый .xlsx;
   - AirScript отпадает.
3. **PDF** — необязательно, после MVP.
4. **Возможно, несколько пользователей.** Сразу закладываем организации, участников и роли, но MVP работает и для одного человека.

## 7. Универсальный движок расчёта

Обе модели укладываются в один конвейер. Шаги включаются и настраиваются для **каждого отдела** отдельно:

```
1. ОСНОВА (по отделу выбирается одно):
   а) Баллы:          Σ (кол-во действия × баллы действия) × цена балла
   б) Доля бюджета:   бюджет отдела × % вклада   (бюджет отдела = остаток × вес)
   в) Фикс. ставка:   ставка по должности/рангу
   г) Вручную:        сумма вводится руками
2. МНОЖИТЕЛЬ:      × множитель должности/ранга (по умолч. 100%)
3. БОНУСЫ/ШТРАФЫ:  ± разовые корректировки с комментарием (видны в отчёте)
4. ЛИМИТ:          MIN(сумма, недельный максимум)  — общий или по должности
5. ОКРУГЛЕНИЕ:     вниз до N (1, 100, 1000); остаток → правило (никому / наибольшему вкладу / пропорционально)
6. ВЫПЛАТА:        способ выплаты → комиссия (%), к выдаче
```

- **LSPD:** у всех отделов основа «Баллы», множитель по должности, лимит 250 000, комиссия 2,91% за электронную выплату.
- **SASPA:** у Офиса «Фикс. ставка» по рангу, у остальных «Доля бюджета», округление до 1000, распределение остатка.
- **Справочники организации** (всё настраивается): отделы (цвет, порядок, основа расчёта), должности и ранги (множитель, ставка), каталог действий (код, название, баллы, отделы, где действие доступно, архивное или нет), способы выплаты (комиссия).
- **Снимок настроек:** при открытии недели настройки копируются в неё. Изменение тарифов не меняет закрытые недели.
- **Объяснимость расчёта:** у каждой суммы есть раскрытие «как посчитано» (основа → множитель → лимит → комиссия). Это же уходит в отчёт для админов.

## 8. Отчёт для админов (WPS .xlsx)
- **Лист «Итог»:** период, организация, сводка (сотрудников, начислено, комиссия, к выдаче, выдано / не выдано), таблица по отделам.
- **Лист «Детализация»:** сотрудник × действия (или %), с формулами, чтобы админ видел, откуда сумма.
- **Лист «Тарифы»:** снимок настроек недели.
- **Лист «Журнал»:** правки за неделю (по желанию).
- Шаблон оформления отчёта можно настроить (название, цвета, какие столбцы выводить).

## 9. Архитектура
- **Интерфейс:** React + TypeScript + Vite, Tailwind, TanStack Query; своя таблица ввода; ExcelJS для отчёта.
- **Сервер:** Supabase, бесплатный тариф (решено 24.11.2026; требование — ноль рублей в месяц).
  - Postgres + Row Level Security: каждая организация видит только свои данные.
  - Вход через Discord OAuth (привычно для RP-сообществ) или e-mail.
  - Realtime: несколько человек видят правки друг друга.
  - Лимиты бесплатного тарифа: база 500 МБ, 2 проекта. Для фракций этого хватит на годы.
- **Защита от паузы и резервные копии.** На бесплатном тарифе Supabase ставит проект на паузу после 7 дней без запросов, а после долгой паузы восстановить его в один клик уже нельзя. Защита в три слоя:
  1. **Пинг:** cron-job.org (бесплатно) раз в 2–3 дня делает запрос к базе: читает одну строку из служебной таблицы `heartbeat` через REST с anon-ключом. Таблица доступна только на чтение.
  2. **Еженедельная резервная копия:** GitHub Actions по расписанию делает `pg_dump` и коммитит дамп в **приватный** репозиторий.
     - Это одновременно второй пинг и собственные копии: на бесплатном тарифе Supabase скачиваемых копий нет.
     - Коммит при каждом запуске не даёт GitHub отключить расписание за неактивность (правило 60 дней).
     - Хранить последние N копий, старые удалять.
  3. **Обычная работа:** приложение, которым пользуются еженедельно, само держит проект активным.
  - В документации: инструкция «как поднять базу из дампа в новом проекте Supabase» и проверка восстановления хотя бы один раз.
- **Слой данных за интерфейсом.** Приложение работает с хранилищем через свой интерфейс (repository). Реализации: браузерная (прототип) → Supabase. Если Supabase отпадёт, меняем только этот слой (запасные варианты: Firebase Spark, PocketBase).
- **Роли (решено 25.11.2026):**

  | Роль | Где | Что может |
  |---|---|---|
  | Суперадмин (вы) | вся платформа | создаёт организации, выдаёт и снимает доступ админам сервера, всё, что могут админы |
  | Админ сервера | **все организации** (решено 25.11.2026) | **назначает и снимает лидеров**; проверяет: видит недели, ведомости, архив, журнал, скачивает отчёты; данные недель не меняет |
  | Лидер (владелец) | своя организация | настройки, участники (в т.ч. заместители), ввод, ведомость, закрытие недели, отчёты |
  | Заместитель лидера | своя организация | ввод, ведомость, закрытие недели, отчёты; **назначает и снимает участников** (начальников отделов и состав); без настроек |
  | Начальник отдела | свои отделы | **только вносит баллы / % вклада**; суммы, ведомость, отчёты и статистику в деньгах **не видит** |

  Правило назначений: управлять можно только ролями ниже своей. Админ — лидерами; лидер — заместителями и ниже; заместитель — начальниками отделов и составом. Заместитель не может снять лидера или другого заместителя, лидер не может снять сам себя (только передать роль). Все назначения и снятия пишутся в журнал.

- **Изоляция организаций** — на уровне базы (Row Level Security): строки помечены организацией, участники других организаций их не получают даже прямым запросом. Один человек может состоять в нескольких организациях (переключатель).
- **Организации создаёт суперадмин (решено 25.11.2026).** Самостоятельной регистрации организаций нет: вы создаёте организацию и отправляете лидеру ссылку-приглашение, лидер сам приглашает заместителей и начальников отделов.
- **Начальник отдела (решено 25.11.2026):** экран ввода показывает только его отделы (их может быть несколько), без столбца «Начисленно» и без денег вообще — только баллы или % вклада. Скрыть деньги нужно и на сервере (отдельное представление без сумм), а не только в интерфейсе.
- **Вход через Discord без бота:** обычный OAuth (scope `identify`), на сервер фракции ничего не добавляется. Позже по желанию — автоназначение ролей по ролям на Discord-сервере фракции (scope `guilds.members.read`, тоже без бота).
- **Расчёт** — чистая функция на TypeScript с тестами. Одна и та же функция считает на экране и в отчёте.
- **Хостинг:** Vercel или Cloudflare Pages + Supabase free tier.

## 10. Порядок работы
1. ✅ **Кликабельный прототип без сервера** (готово 24.11.2026). Данные в браузере. Шаблон LSPD с вашими реальными данными: экран недели, ведомость, закрытие недели, скачивание отчёта .xlsx. Проверяем скорость ввода и удобство.
2. ✅ **Движок + настройки** (готово 24.11.2026): конструктор отделов, должностей, действий и правил; шаблоны LSPD и SASPA; тесты расчёта на цифрах из обеих таблиц. Сверх плана:
   - своя цена балла у отдела, «обычный максимум» действия за неделю, доступность действий по отделам;
   - веса отделов в обе стороны (меняешь % или сумму), калькулятор «Проверка расчёта»;
   - предупреждения движка (сумма % ≠ 100, веса ≠ 100, ставки больше бюджета, нет паспорта, превышение максимума) и кнопка «до 100%»;
   - мастер новой организации, экспорт и импорт настроек как шаблона;
   - массовый импорт сотрудников вставкой из WPS / Excel / Google (колонки определяются сами, «РВ» кириллицей = PB);
   - версия схемы данных и миграция сохранённых данных;
   - «Добить до бюджета» больше не нужен: бюджеты отделов и доли делятся методом наибольших остатков, поэтому при весах и % = 100 начислено ровно равно бюджету (проверено тестом на 1 200 случайных неделях).
3. **Сервер:** Supabase, вход, организации, роли, приглашения, журнал правок, realtime. Сюда же входят пинг через cron-job.org и еженедельная резервная копия через GitHub Actions.
4. **Статистика, карточки сотрудников, публичная ссылка на итог,** импорт сотрудников из .xlsx.
5. **После MVP:** PDF, Discord-уведомления о выплатах, импорт старых архивов.

## 11. Живучесть без автора (требование 25.11.2026)

Цель: если автор перестанет заниматься проектом, приложение продолжает работать без него.

**Ни один критичный аккаунт не принадлежит одному человеку:**

| Что | Где | Как застраховать |
|---|---|---|
| Код и сайт | GitHub Organization (бесплатно) | 2+ владельца организации; сайт на GitHub Pages — бесплатно, без «засыпания», адрес `*.github.io` не истекает |
| Резервные копии базы | приватный репозиторий в той же организации | копия раз в неделю через GitHub Actions; каждая копия — коммит, поэтому расписание не отключается |
| База и вход | Supabase organization | 2+ участника с правами владельца |
| Вход через Discord | Discord Developer **Team** | приложение принадлежит команде, а не личному аккаунту; 2+ владельца |
| Пинг от паузы | GitHub Actions (основной) + cron-job.org (запасной) | основной пинг живёт в организации GitHub, не на чьём-то компьютере |

**Внутри приложения:**
- суперадминов может быть несколько; последнего снять нельзя;
- админы сервера сами назначают и снимают лидеров — повседневная работа не требует автора;
- лидер в любой момент скачивает все данные своей организации (.xlsx и .json).

**Без платного и без ручных шагов:**
- ни платных сервисов, ни своего домена, который надо продлевать;
- ни ключей с истекающим сроком;
- ни задач, которые кто-то должен запускать руками (кроме закрытия недели лидером — это его работа).

**Код публичный, сайт на GitHub Pages (решено 25.11.2026)** — проект некоммерческий.

**Продукт стартует с чистого листа (решено 25.11.2026).** Первый запуск — экран приветствия: «Создать организацию» или «Восстановить из копии». Демо-данные — только для разработки (`src/dev/demo.ts`, видны при `npm run dev`, в продакшен-сборку не попадают); игроки в демо выдуманные, количества действий — из реальной недели WPS, чтобы тесты сверяли расчёт до рубля. Публичный репозиторий выкладывается одним чистым коммитом, без истории с реальными данными.

**Безопасность при открытом коде.** Код можно держать публичным: секретов в нём нет, доступ к данным закрыт правилами в самой базе (RLS). Ключ доступа к базе для сайта — публичный по назначению; служебный ключ хранится только в секретах GitHub Actions.

**HANDOVER.md** — инструкция для преемника:
- где что лежит и кто владельцы;
- как добавить нового владельца;
- как восстановить базу из копии;
- что делать, если Supabase ушёл в паузу или закрыл бесплатный тариф (запасной путь — PocketBase из той же копии).
